### 18:55–19:12 主页 jsDelivr 双源加速上线
- **做了什么**：主人拍板 jsDelivr 方案。app.js 改造：①新增 cdnFetchJSON——data.json、单篇正文、搜索索引全部「jsDelivr CDN 优先 → 失败自动回退 GitHub 直连」；②音频 src 改 CDN 地址 + data-local 存本地回退，<audio> error 事件自动切换（每篇回退一次）；③声线切换按钮同步改造（偏好判断从 CDN src 改为比对 data-local，修掉一个判断失准的隐患）。推送 35639dd 后调 purge.jsdelivr.net 即时刷新 data.json/search.json 的 CDN 缓存（解决 jsDelivr 对分支 12 小时缓存的时效问题——只有被更新过的两个大文件需要 purge，1714 个单篇 JSON 首次请求必然回源，无旧缓存风险）。实测：首页 data.json 走 CDN 888ms 加载、文章页正文/音频均命中 jsDelivr、回退字段就位。
- **发现的问题**：jsDelivr 对 GitHub 分支资源有最长 12 小时缓存——用 purge 接口按需刷新即可，无需为时效放弃加速。
- **怎么解决的**：双源设计的关键是「回退路径永远是直连」——CDN 抽风时最坏情况等于现在的速度，不会更糟。
- **学到了什么**：CDN 加速的不是带宽是 RTT——174KB 的 data.json 从 1160ms 降到边缘节点一跳；发新内容后 purge 两个固定文件（data.json/search.json）应写进收口清单，不然新故事最长半天不可见。
