### 01:45–02:35 模型下载 8GB + 双服务上线，踩掉两个大坑
- **做了什么**：modelscope 单连接只有 1MB/s 还顺带拖 onnx 冗余文件，弃；改用主人的 pdl.sh 16 连接从 hf-mirror 拉 Qwen3-8B-AWQ（6.1GB）+ bge-m3（2.3GB），全部校验通过。vLLM 复用现成镜像起两个容器：bge-m3 走 --runner pooling（:8001），Qwen3 走 --reasoning-parser qwen3（:8002）
- **发现的问题**：① Qwen3 引擎起不来，报 "UVA is not available"——翻镜像里源码发现 WSL2 下 vLLM 默认禁用 pinned memory，藏着个 VLLM_WSL2_ENABLE_PIN_MEMORY=1 的开关；② LightRAG 自带的 openai_embed 装饰器写死 1536 维还忽略手动传参，对着 bge-m3 的 1024 维疯狂报维度错误
- **怎么解决的**：① 容器加环境变量；② 弃用自带函数，用 openai SDK 自己写了 15 行 embedding 函数
- **学到了什么**：报错说"UVA 不可用"，真凶是 pinned memory 被默认关掉——dev 版镜像的隐藏开关只能读源码挖，猜是猜不出来的

### 07:45–08:20 调研 Qwen3.8 系列：没有适合 24G 的量化版
- **做了什么**：主人问 qwen3.8 系列的量化小模型哪个适合本机——原来 "qwen3.8" 是 8 月新发布的系列，不是我装的 Qwen3。搜索配额还挂着，改用 hf-mirror 的 API 直接列 Qwen 官方仓库：3.8 系列只有 27B（dense）、Flash-Next（名义小杯，实际 125B 激活 6B + 51B n-gram 嵌入 ≈ 总权重 180B）、2.4T-A95B 三款。把 27B 各家量化版体积逐一查实：官方 FP8 27GB、unsloth NVFP4 23.4GB、AWQ-INT4 21GB、GPTQ-Int4 最瘦 19.6GB
- **发现的问题**：4-bit 只压 transformer 核心（约 13.5GB），25 万词表的 fp16 嵌入层 + MTP 模块占 6~8GB，所有量化版都 ≥19.6GB——塞进 24G 后 KV 缓存只剩约 2GB，RAG 入库那种多并发长上下文负载直接废掉
- **怎么解决的**：结论"暂时没有适合的"，现有 Qwen3-8B-AWQ 就是这台 24G 卡跑 RAG 的甜点位；顺带在镜像源码注册表里确认已支持 qwen3_5 架构，等 3.8 出 9B/14B 小杯可无缝替换
- **学到了什么**：MoE/混合架构的"激活参数小"是话术陷阱，占显存的是总权重；查模型最新动态不用等搜索配额，hf-mirror 的 API 能把官方仓库列得明明白白

### 08:30–10:30 客服前端上线：微信式对话 + 流式输出 + 可打断
- **做了什么**：给问答系统做了"客户↔客服"风格网页（app.py + web/index.html，FastAPI 包 LightRAG，SSE 流式）：微信式气泡、正在输入动画、5 种检索模式切换、快捷问题、引用溯源折叠面板。主人提"一直思考中能不能打断"，又加了"■ 停止"按钮——客户端 AbortController 掐断连接，后端锁随取消即时释放，实测打断后第二问 6.1 秒完成，不用等后台跑完
- **发现的问题**：① LightRAG 1.5.7 必须显式 await initialize_storages()；② QueryParam 字段全改名（默认上下文预算 30000 token 比模型 24k 窗口还大，首轮查询直接 400）；③ 服务端 16k 上下文配合长检索结果太挤
- **怎么解决的**：① 补异步工厂 create_rag()；② 按新字段名收紧预算（max_total_tokens=8000 等）；③ 服务端 max-model-len 提到 24576
- **学到了什么**：POST+SSE 用 fetch+ReadableStream 手搓解析比 EventSource 灵活；"可取消"要靠 AbortController 从客户端一路取消到后端锁，链路上任何一层吞掉 CancelledError（它继承 BaseException，不是 Exception）就会漏

### 10:40–11:10 联网搜索上线：ddgs 免 key 并行检索
- **做了什么**：主人要免 API 的联网搜索。实测三路：ddgs 库（pip 装，免 key）直接可用；公共 SearXNG 实例的 JSON 接口全是人机验证页；百度 302 反爬。随后给前端加了 🌐 联网搜索开关：开启后 asyncio.gather 并行跑 ddgs 网页搜索 + 知识库上下文检索，两边资料拼进提示词综合作答，来源以 SSE 事件推给前端，答案下渲染可点击的来源链接。浏览器实测：问"哈利波特电影的男主角是谁"（红楼梦知识库必然答不了），正确答出丹尼尔·雷德克利夫并附 6 条来源

- **学到了什么**：asyncio.gather 把两路检索并行，总延迟取 max 而不是 sum；免 key 搜索的首选就是"匿名抓取库 + 自建 SearXNG"两条路，公共实例靠不住
