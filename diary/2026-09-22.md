### 08:20–08:55 配音收官 + 揪出"配音没接上线"的大乌龙
- **做了什么**：昨晚续跑的 184 个完成（173 ✓ / 11 ✗，379 分钟），mp3 总量 1554。顺手验证站点时揪出大问题：data.json 的 audio 字段指向旧目录 assets/audio，**这几天合成的上千个新配音根本没被站点引用**——一直在给一个没插电的音箱充电。修复分四步：①build_site.py 的 audio 字段改为优先 ds-audio、回退旧人声；②发现 .gitignore 里赫然写着 assets/ds-audio/——配音文件从来没进过仓库，线上 404；③ds-audio 实际 3GB（含 437 个无引用孤儿 mp3，0.81GB），远超 GitHub Pages 1GB 站点上限——删孤儿 + ffmpeg 4 路并行重编码（48kbps mono、24kHz 采样，语音完全够用）压到 1.2GB；④移除 .gitignore 规则，1119 篇配音入库（commit 30763c6），1.2GB 的 push 挂在后台慢慢传。
- **发现的问题**：①剩 11 个失败项里 9 个科普是"稳定超时"——同样的文本上一轮也全败（为什么先看见闪电/微波炉加热/冰箱制冷这类"为什么"标题），DeepSeek 复述这类文本时 REPLY_TIMEOUT，不是偶发，重试大概率还败；②重编码采样才发现源文件本来就是 48kHz 单声道 90kbps，压到 48k mono 收益刚好砍半。
- **怎么解决的**：配音接入与压缩已完成并推送；9 篇科普留作长尾（1119/1129 = 99.1% 覆盖，缺的篇目前端有浏览器朗读兜底，体验不断）。它们需要换个解法——比如文本预清洗（问句改陈述？）或单篇排查，明天试。
- **学到了什么**：三层叠加的乌龙一次全露馅：管线在跑 ≠ 数据在库里，库里 = ≠ 站点在用——上线验证必须"最终用户视角"走一遍（音频 URL 404 就是这么发现的）；.gitignore 里躺着一行旧规则能吞掉整个功能；仓库体积要在提交前算账（du 一下），Pages 的 1GB 红线是真的。

### 09:10–11:14 最后 10 篇配音破案：真凶是 Markdown 列表前缀
- **做了什么**：9 篇科普的"稳定超时"不肯善罢甘休，做对照实验：取 02-闪电雷声预处理（问号转句号）单篇跑——第 1 段 36 秒成功、第 2 段照样 REPLY_TIMEOUT，问句假设被证伪。把第 2 块文本打出来肉眼看，真凶现形：**`- 声速：每秒约 340 米…` 这样的 Markdown 列表前缀没被清洗**，extractReadingText 清了图片/斜体/链接/引用行唯独漏了它。带列表符号的文本让 DeepSeek 倾向"整理回答"而非原样复述，probe 匹配失败就等满 240 秒报超时——这解释了为什么 9 篇全败（它们正文都是"光速：…；声速：…"列表体）而同分类 90 篇正常。修复 batch_stories.js（加无序/有序列表前缀清洗）后重跑：**10/10 全过、零失败，只花 10 分钟**（此前 148 分钟只磨出 2 个）。新文件压到 48k mono 统一口径，data.json 配音覆盖 1129/1129 = 100%，推送部署验证（科普 02 音频 200）。
- **发现的问题**：push 时遇到一次 TLS unexpected eof，等 10 秒重试即过——大 push 之后偶发，不是网络坏了。
- **怎么解决的**：全库 1129 篇、21 分类、**100% 配音覆盖**正式收官。从 9-20 启动配音到今天全部齐了。
- **学到了什么**：破案的关键一步是"把失败块的文本打出来肉眼看"——对照实验证伪问句假设后没有硬试，而是直接看数据，列表符号一眼就露馅；"稳定失败"从来不是运气差，是确定性 bug 在等着被发现。清洗函数每接一种新 Markdown 元素就要想一遍还有没有漏网的——列表、表格、脚注，一个都不能少。

### 23:20–00:10 首屏提速：data.json 拆分瘦身，首屏传输降 92%
- **做了什么**：主人反馈"网页第一次加载很慢，想先加载文字后加载音频"。排查发现真凶不是音频（audio 标签本就是 preload="none"，不点不下载），而是 **data.json 已膨胀到 6.8MB**——1129 篇的正文全文全塞在里面，首屏必须等它下完。方案：①build_site.py 把正文/结尾/小启示拆到 docs/story/<分类>/<编号-标题>.json（1129 个单篇小文件，2-4KB）；②data.json 只留列表字段（标题/元信息/摘要/音频路径），6.8MB→686KB；③app.js 文章页先渲染标题+元信息骨架（"正文加载中…"），fetch 单篇 JSON 后填充正文，浏览器朗读兜底改用加载完的 plain，搜索改为标题+摘要+元信息（降级了全文搜索）。推送 b0744fb，线上验证：单篇 JSON 200，data.json gzip 传输仅 **141KB**（此前约 1.8MB，降 92%）。
- **发现的问题**：①部署中途又是新旧资源不同步（data.json 已新版、单篇 404），等 built 再验就好；②改 app.js 时手滑写错过两处（fs + -2、old_string 抄错字母），靠复读代码抓回来。
- **怎么解决的**：提交前 node --check 校验语法 + grep 残留引用（s.content/s.plain/s.ending/s.card 已零残留）。
- **学到了什么**："音频加载慢"是用户的猜测，数据才是真相——量了 data.json 才知道 6.8MB 的首屏包袱；性能优化先量再改。搜索降级全文这个取舍要向主人说明：现在搜不到只在正文出现的词了，需要的话可以后续加纯文本搜索索引。
